# CI

Four GitHub Actions workflows in [`.github/workflows/`](../.github/workflows/).
All run on pull requests and on pushes to `main`.

| Workflow | Triggers on changes to | Does |
|---|---|---|
| `ai-service.yml` | `ai-service/**`, `docs/fixtures/**` | ruff lint + format check, pytest |
| `api-service.yml` | `api-service/**` | `./mvnw -B verify` (unit + Testcontainers) |
| `web.yml` | `web/**`, the api OpenAPI spec | eslint, `tsc --noEmit`, generated-types check, vitest, build |
| `contracts.yml` | always | Redocly lint + drift check |

Path filters mean a frontend PR doesn't wait on a Maven build. `contracts.yml`
runs on everything, because it's the one guarding the thing both halves depend on.

## Branch protection

Set on `main` once the first real code lands:

- Require a PR — no direct pushes.
- Require one approving review from the other person.
- Require these checks to pass: `contracts / lint`, `contracts / drift`, plus
  whichever service workflows the PR triggered.
- Require branches to be up to date before merging.
- No force pushes, no deletion.

## Notes on each

### `contracts.yml`

Two jobs.

**`lint`** runs Redocly against both specs using the rules in
[`redocly.yaml`](../redocly.yaml). Three `recommended` rules are switched off
there with reasons in comments — localhost server URLs, no license block, and
4xx responses on the health probes. Everything else is on.

**`drift`** is the interesting one. It fails a PR that touches route files
(`api-service/.../controller/`, `ai-service/app/routers/`) without touching
`docs/03-API-CONTRACT.md` or `docs/contracts/`.

This catches the specific thing that hurts us: someone adds an endpoint, the
other person doesn't know, and it's discovered three days later during
integration. It's a heuristic — it can't tell an interface change from an
internal refactor in the same file. When it's wrong, add the
**`contract-unchanged`** label. Using that label to skip writing the contract
down is the one thing it can't protect against.

It also warns (doesn't fail) when the Markdown contract and the OpenAPI specs
move independently, since they're meant to stay in lockstep.

### `ai-service.yml`

- Python **3.11**, matching the Dockerfile. Not the runner default — see the
  version note in [07-LOCAL-DEV.md](07-LOCAL-DEV.md).
- Installs CPU-only torch from the PyTorch index. Without it, CI pulls ~2 GB of
  CUDA wheels for a runner with no GPU, and the job takes ten minutes longer.
- Caches `~/.cache/huggingface`, so the embedding model downloads once rather
  than on every run.
- `OLLAMA_BASE_URL` points at a dead port on purpose. There's no Ollama in CI;
  tests stub the HTTP calls with `respx`. If a test ever hits the network for
  real, it fails immediately instead of hanging until the job timeout.

### `api-service.yml`

`mvn verify` runs the Testcontainers integration tests, which need a Docker
daemon. `ubuntu-latest` has one. macOS runners don't, so don't switch the
runner without reworking those tests.

Surefire reports upload on failure — a stack trace in an artifact is easier to
read than one in a folded log.

### `web.yml`

The generated-types step is the one worth understanding. `src/api/types.ts` is
generated from `docs/contracts/api-service.openapi.yaml` and committed. CI
regenerates it and fails if the result differs from what's checked in.

That means a contract change can't quietly leave the frontend compiling against
old shapes — the build breaks in the PR that changed the contract, which is
exactly where you want to find out.

## What CI does not do

- **No deploy.** Local Docker only, per [00-PROJECT-BRIEF.md](00-PROJECT-BRIEF.md).
- **No image publishing.** Images are built locally by Compose.
- **No coverage gate.** A percentage would push us toward tests that pass rather
  than tests that catch things. The list in [08-TESTING.md](08-TESTING.md) of
  cases that must be covered is the real requirement.
- **No end-to-end tests.** Nothing runs the three services together in CI. The
  contract lint plus the drift check plus the WireMock stubs copied from contract
  examples are the substitute, and they're weaker — real integration is verified
  by hand with `./scripts/seed.sh`.

## When CI is slow

First `ai-service` run after a `requirements.txt` change is ~8 minutes (torch).
Cached runs are ~2. `api-service` is ~4 minutes with a warm Maven cache, longer
on the first run because Testcontainers pulls the Mongo image.

If a workflow times out rather than failing, check the Ollama and network
assumptions above — a hanging job is almost always something reaching for a
network resource that isn't there.
